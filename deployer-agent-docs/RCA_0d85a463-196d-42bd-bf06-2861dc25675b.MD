# RCA — DU-NZO deploy failed at pull_source (run 0d85a463-196d-42bd-bf06-2861dc25675b)

## Symptom
Initial deploy failed at the first pipeline step. Error:
```
prepare build context: read envs: read env file backend/.env:
open /tmp/.../app/backend/.env: no such file or directory
```

## Immediate cause
The deploy run was provisioned with:
- `template = fastapi_react_mongo_shadcn_base_image` (the FARM React+FastAPI template)
- `frontend_type = cloudflare`

The FARM template's `config.yaml` declares `env_paths: ["backend/.env", "frontend/.env"]`.
pull_source tries to read `backend/.env` to cache the app's env vars. This app has
**no `backend/` directory** — its env lives at `/app/.env` — so the step dies immediately.

## Root cause (why this is NOT a one-line fix)
The app is a **Node.js monorepo**, not a React/FastAPI app:
- Express server `/app/server/src/index.js` serves BOTH the static Vite build
  (`/app/client/dist`) AND the `/api` routes.
- Env file is `/app/.env` (single file; no `backend/` or `frontend/` dirs).
- Runs in preview via a custom `dunzo.conf` with two node programs
  (`dunzo-web` PORT=3000, `dunzo-api` PORT=8001) — not the template supervisor.

The assigned FARM + cloudflare template is incompatible at every layer, so fixing only
`env_paths` would just move the failure downstream:
1. **pull_source** — `env_paths` points at `backend/.env` (does not exist). ← current failure
2. **build_image** — FARM `Dockerfile.cloudbuild` runs `pip install backend/requirements.txt`
   and `yarn build` in `frontend/`; neither path exists in this repo.
3. **entrypoint.sh** — parses `[program:backend]` from the standard `supervisord.conf`;
   this app uses `dunzo-web`/`dunzo-api` in `dunzo.conf`.
4. **nginx.conf** — proxies `/api`→127.0.0.1:8001 and serves the SPA from
   `/usr/share/nginx/html`; this app's Express process serves everything itself.
5. **frontend_type = cloudflare** — `build-frontend-artifacts.sh` requires a `frontend/`
   directory, runs yarn, and uploads the build to R2 for a Cloudflare worker to serve +
   proxy `/api` to the pod. This directly conflicts with this app's design (Express serves
   the static site). `frontend_type` is a **deployment-level property that cannot be
   changed by a manifest override.**

## Why I did not attempt a manifest fix
- Writing any manifest (e.g. `config.yaml`) forces the COMPLETE 6-file set to be authored,
  because once any override exists the build loads ALL template files from GCS.
- There is no authoritative base to modify: the farm reference manifests are the wrong
  shape for a Node monorepo, GCS is empty (first deploy), and the eph sandbox cannot
  provide the source (pull_source never produced a source archive — `eph_source_access_failed`),
  so COPY paths (`client/dist`, `server/src/index.js`, package layout) cannot be verified.
- This is the "cannot assemble the complete set from authoritative sources → do NOT
  fabricate → escalate" case. And even a perfect Dockerfile cannot reconcile the
  `cloudflare` frontend_type with an Express-serves-everything app.

## Recommended fix (platform / deployment re-provisioning)
Re-create this deployment with the correct template for a Node.js monorepo — the `mono`
template family — and `frontend_type = kubernetes`, so the Express server serves both the
static Vite build and `/api` in-pod exactly as it does in preview. The single env file
`/app/.env` must map to the template's `env_paths` (one `.env`, not `backend/.env` +
`frontend/.env`). This cannot be achieved by a manifest override on the current
FARM + cloudflare deployment.
